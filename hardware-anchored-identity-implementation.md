### Hardware platform for the demo

Pick one and document its exact guarantee. Recommendation: **Azure confidential VM (AMD SEV-SNP
with vTPM)** with **Azure Attestation** as verifier, called by the attestation script
(`verifier_kind=azure-maa`). The verifier returns an `AttestationResultJWT` (one script branch, no
quote parsing); the result covers the SEV-SNP launch measurement and the vTPM-held key, so
`platform=azure-cvm-sev-snp`; the agent key is generated in the vTPM with
`fixedTPM | fixedParent | sensitiveDataOrigin` and certified to the AK with `TPM2_Certify` (§9.3a).
What it proves: the private half of `K` is inside the vTPM of a VM whose launch measurement Azure's
verifier appraised, and the appraisal is no older than the configured maximum at each issuance. What
it does not prove: which process inside the VM asked the vTPM to sign (§15), nor — pending captured
vectors — the AK-to-VM binding that `certified` depends on (§9.3a AK-binding gap). Fallback: a plain
**TPM 2.0** host (`platform=tpm2`), which needs the in-process quote script and an AK certificate
chain to a manufacturer CA.

## Test design

Project rules apply: TestNG + Mockito, `@Listeners(MockitoTestNGListener.class)`, `lenient()` for
shared stubs, a test class is named after the class under test plus `Test`, all `@Test` methods
above helpers, no section-divider comments. Third parties never appear in unit tests
(`WebKeysConfiguration`, `AppConfiguration`, `ConfigurationFactory`, `AbstractCryptoProvider`,
`CommonUtils` are mocks or `mockStatic`).

The "Covers" column lists **required behaviors each test must assert**, not guarantees already
established. A behavior stated here is a test obligation; the durability and ordering behaviors
(single-row state, journal fencing, staged-commit recovery, enrollment init) are only *established*
once the crash-point and concurrency fault tests below pass on SQL. Until then the review
history marks those items partially resolved.

covers all three kinds (`TokenEntity`, `KeyEnrollment`, `AttestationAssessment`, each carrying its `operation_id` receipt); **the crash-after-entity-transaction-committed-before-emit case** — the entity + `IssuanceLog` + flip committed, process died before delivery — is resolved to `committed` and the success record **delivered** (the `IssuanceLog` probe finds it even after the token is TTL'd away), **never** aborted; an entry whose `operation_id`-keyed `IssuanceLog` is absent **but** younger than `resolutionWaitSeconds` stays `staged` (unresolved) and is retried; **past the wait with the `IssuanceLog` absent → `aborted`** and an aborted-outcome record delivered — because the `IssuanceLog`/entity/flip are one SQL transaction, absence past the wait is **decidable non-commit**, so there is no undecidable case (no `indeterminate`); token **absence is never failure** — an SVID whose `IssuanceLog` is present but whose `TokenEntity` expired/was revoked is `committed`; **fencing:** before the terminal `aborted` outcome recovery cancels the entry (CAS the `fence`), and a **paused writer that resumes cannot commit** — its fenced entity transaction is rejected (so recovery never races a late commit); a `staged` entry is **never** expired by TTL; chain stays gapless for both outcomes; retention satisfies `≥ resolutionWaitSeconds + maxExpectedDowntimeSeconds + reconciliationIntervalSeconds` |
| `OutcomeRecordSchemaFixtureTest` | **per-operation-kind wire-contract fixtures (§11.2):** a canonical JSON fixture for **each (operation kind × outcome)** cell — issuance / enrollment / appraisal / bootstrap, each in `committed` / `aborted` — validated against the record schema and asserted to **round-trip byte-identically through `jans-trace-core`** (the shared validation + canonicalization, the same bar as `TraceRecordBuilderTest`). Each fixture asserts: `provisioning_outcome` is one of `{committed, aborted}`; **`credential_fingerprint` present iff `committed`** — a `committed` fixture missing it and an `aborted` fixture carrying it are both **rejected**; `reason` is `not_committed` for `aborted`; `sequence_number`, `prev_record_hash`, `trace_execution_id`, `execution_authority`, `subject`, and the success record's `parent_record_ids` are present on every outcome; **producer-key scope:** the issuance/enrollment/appraisal fixtures are `CREDENTIAL_PROVISIONED` and verify only under the `jans-svid-issuer` key, the bootstrap fixtures are `EXECUTION_STARTED` and verify only under the `jans-auth` key, and a bootstrap-abort fixture mis-encoded as `CREDENTIAL_PROVISIONED` is **rejected** (wrong kind for the producer). ## Crash-point and concurrency fault tests

The durability and ordering guarantees in §§9.3c, 9.5, 9.7, 10.4, and 11.3 hold only if these tests
pass; until they do, treat the corresponding claims as **asserted-but-unverified** (the review
history marks the items partially resolved). These tests run on the **issuer-side SQL transaction
domain** (§11.3) — the entity and evidence tables in one `jans-orm` SQL database (MySQL 8+ /
PostgreSQL), the backend this feature requires — including a clustered configuration, since the
concurrency and crash-recovery paths are what they probe. One test asserts the **startup gate**:
`SPIFFE_SVID_ISSUANCE` with a non-SQL `PersistenceEntryManager` fails closed. Crashes are simulated
by a fault-injecting `PersistenceEntryManager` wrapper that aborts after a named write, including
mid-transaction (asserting the whole **Commit** transaction — entity + `IssuanceLog` + flip — rolls
back atomically, never partially).

- **Crash point between every durable write.** For each ordered multi-write sequence, inject a
  crash after each individual write and assert recovery reaches a correct terminal state with no
  lost or duplicated effect. The sequences and their required recovered outcomes:
  - **Enrollment (§9.5):** steps 1–6 are one SQL transaction (`KeyEnrollmentClaim` insert →
    `KeyEnrollment` → `KeyAttestationState` init → client attribute). Inject a crash after each
    write and assert the transaction **rolls back atomically** — none of the entities exist and the
    client can re-register cleanly; a crash after commit leaves the full enrollment and a re-register
    finds the claim with its own `operationId` and is an idempotent no-op. **Concurrency:** two
    enrollments with the same `attestation_id` for different clients run concurrently; the first to
    commit wins and the second's claim insert violates the unique constraint and its whole
    transaction rolls back (`assessment_already_enrolled`) — exactly one binding exists.
  - **Issuance / enrollment / appraisal (§11.3 transitions):** crash after **Intake**, after **Stage**
    (the journal insert, `staged`), after the **Commit** entity transaction (entity carrying its `operation_id` commit
    receipt + `operation_id`-keyed `IssuanceLog` + `staged → committed` flip, all one SQL
    transaction — `TokenEntity`, `KeyEnrollment`, or `AttestationAssessment`). Recovery decides by
    **matching this entry's `operation_id`** against the entity's receipt or the `IssuanceLog`,
    never by identifier existence — assert a seeded same-identifier entity from a *different*
    `operation_id` does not resolve the entry. Each is resolved to exactly one of `committed` /
    `aborted` / still-`unresolved`, and **a credential that committed is never `aborted`, a
    credential that did not commit is never delivered as success.** The **crash-mid-entity-transaction
    case** rolls back atomically (no partial entity, no `IssuanceLog`) → resolved `aborted` once past
    `resolutionWaitSeconds`; the **crash-after-the-entity-transaction-committed-but-before-the-emit**
    case → resolved `committed` (the `IssuanceLog` survives even after the token is TTL'd away).
    Because the `IssuanceLog`/entity/flip are one transaction, absence of the `IssuanceLog` past the
    wait is **decidable non-commit** — there is no undecidable case. Assert a longer
    `resolutionWaitSeconds` does not change a decided outcome.
  - **Verifier worker (§9.3c):** crash after the assessment write, after `completed`, after the
    state overwrite. Recovery (under the current lease) finishes the remaining steps idempotently;
    `appraisalGeneration`/immutability make replays safe.
  - **Attestation state write (§10.4):** crash between the state overwrite and the TRACE emission
    for that overwrite; the two reconcile without double-applying.
- **Voided/aborted middle-record chain test.** Allocate positions *n-1, n, n+1*; let *n* resolve to
  `aborted` (its credential never committed). Assert Lock receives a **gapless** chain: *n* is
  delivered as an aborted-outcome record, `prev_record_hash` of *n+1* is over *n*'s delivered
  digest, and no `coverage_gap`/`chain_link_failure` is raised. Repeat with the crash injected
  between *n*'s resolution and *n+1*'s hash binding.
- **Stale-worker insertion after fencing.** A verifier worker (or journal writer) whose lease
  expired and was reclaimed at a higher `epoch` attempts its guarded write; assert it is **rejected
  at the write** (no fenced-but-committed row, no forked chain position, no out-of-order state
  overwrite), and that the reclaiming worker's write is the one that lands.
- **Paused writer resumes after recovery cancelled the entry.** Pause the issuance thread *before*
  its step-4 entity commit; let recovery cancel the `staged` entry (CAS its `fence`) and record a
  terminal `aborted` outcome; then resume the paused writer and let it attempt the
  entity write + flip. Assert the resumed write is **rejected by the fence** — it cannot commit the
  credential behind recovery's back — so there is no credential that exists while its position was
  recorded as not-provisioned. Mirror the ordering: a writer that committed *before* cancellation
  leaves a witness recovery sees and is resolved `committed`.
- **Delayed-positive-after-rejection.** A slow `affirming` appraisal with generation `g′` arrives
  after a `contraindicated` with generation `g″ > g′` has been written; assert the slow write is
  **dropped** by the `appraisalGeneration` guard and the row stays `contraindicated` (§10.4). Also
  the inverse: a genuinely newer `affirming` (`> ` the current generation) does overwrite.
- **First-enrollment state initialization.** From no `KeyAttestationState` row, a first enrollment
  initializes it at `revision = 0` and a subsequent `/token` issues; a pre-enrollment assessment
  that is `supersedesEligible=false` still initializes (authorized by the DCR proof, §9.5), and a
  second enrollment of the same `attestation_id` for a different client is refused
  (`assessment_already_enrolled`).
- **Concurrent same-`attestation_id` enrollment (§9.5).** Two registrations naming the same
  `attestation_id` for *different* client IDs are fired concurrently against the atomic
  `KeyEnrollmentClaim` insert-conditioned-on-absence. Assert **exactly one** wins (gets a
  `KeyEnrollment` binding and an initialized `KeyAttestationState`) and the other is refused
  `assessment_already_enrolled` — interleaving the two at the claim insert, so the
  guarantee holds by the conflicting write and not by a lookup that can be stale. A retry of the
  winner (same `operationId`) is an idempotent no-op; a retry of the loser stays refused.
- **Plural in-flight after rejection (flag off).** Several concurrent `/token` calls that pass
  `stillCurrent(r)` before a rejection commits all complete; assert the count is bounded by
  concurrency (not unbounded re-issuance), that every subsequent call is refused, and that with
  `attestationRequireFreshPerIssuance=true` only one of the same concurrent set succeeds.

Each test asserts the **recovered terminal state**, not intermediate prose guarantees; a guarantee
in §§9–11 that lacks a passing test here is not yet established.
